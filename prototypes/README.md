## 验证了什么

- 控制台错误、外部请求、横向溢出：`_tools/shoot.py` 在桌面 / 手机 / 深色 / 减少动态四种条件下逐页检查，三个方向都是 `ok: no errors, no external requests, no horizontal overflow`。结果在 `screenshots/checks-*.json`。每个页面都带 `default-src 'self'` 的 CSP，外部资源加载不进来。
- 文字对比度：`_tools/contrast.py` 从 CSS 变量算出，浅色和深色都 ≥ 4.5:1，见 `../research/contrast.md`。第一次算时 C 的深色模式绿色状态字只有 2.03:1，已改成单独的 `--green-text` 并复算通过。
- 键盘和焦点（脚本实测，Chrome 156）：A 的 J/Enter/Esc 后焦点回到原来那一行，1 分拣后出撤销提示，U 撤销，⌘K 打开 / 关闭后焦点回去，"定位原文"高亮对应片段；B 的查询词弹层 Esc 后焦点回到触发词，详情 Esc 回到原条目，分拣按 2 换下一份；C 点格口后计数加一、换下一张，按 3 不播动画，详情 Esc 回到原条目。
- 细节工艺清单逐项结果：`../research/craft-details.md` 最后一节。
- 没验证：真机（iPhone / Windows）效果；读屏软件；Windows 上没有苹方、宋体、楷体时的样子（B 受影响最大）。

## 需要你决定的事

1. **选哪个方向**，或者在一个方向上借另一个的某一处（例如 A 的整体 + B 的详情页批注）。
2. **产品名**。原型里的"寻岗"只是占位。
3. 如果选 C：界面里的邮政用语（收件、拆信、退件、格口）要不要保留，还是只留邮戳和分拣格、文案回到普通说法。

字体打包已按你的条件做了（OFL、合计不超过 1.5 MB、中文只子集化界面文字、`font-display: swap`）。实现时字体进 `static/fonts/`，署名进 `THIRD_PARTY_NOTICES.md`，原型阶段没动这两处。

## 为什么推荐 A

这个产品的核心是两件高频的事：在很多条 JD 里找、分、比，以及读一份 JD 时看清"我哪里够、哪里不够"。

- 高频操作要快。A 是唯一一个能全程用键盘做完"搜 → 看 → 分"的方向。Emil Kowalski 和 Rauno Freiberg 都写过：一天用几十上百次的操作，动画和装饰会变成负担。B 的阅读节奏和 C 的隐喻都会在第二周开始拖慢人。
- 荧光笔黄不是装饰，它就是数据：黄底 = 简历里有事实支撑，虚线 = 不知道，波浪线 = 缺少。这正好是 ATS 关键词覆盖要表达的东西，而且读者拿笔划过纸质 JD，一看就懂。
- 跨来源去重和新旧在 A 的列表里最清楚：每行一个状态词加一句话（"2 天前发布，今天官网核验在招"），来源折叠成一行，展开是键值表。
- 下限最高：单字体族加一个强调色，以后加功能时最不容易走样。

A 的风险：它可能还是让人觉得"工具感"，不够有记忆点。验证办法是你实际点一遍 A 的搜索和详情，对比 B 的详情页。如果你更喜欢 B 的详情，我建议用 A 做整体框架、B 的"原文逐段批注"做岗位详情。这两者能拼在一起，因为它们共用同一套状态词和证据高亮。C 的邮戳我不建议直接搬进 A：邮戳的信息量和 A 的一行状态词重复，搬过去只剩装饰。
